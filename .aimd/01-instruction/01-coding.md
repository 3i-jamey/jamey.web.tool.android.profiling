# 코딩 규칙

**코드는 만질수록 복잡해진다.** 판단이 갈리면 더 단순한 쪽을 고른다.

## 워크플로우

작업 단위마다 반복한다: 1. 파악 → 2. 완료 조건 → 3. 구현 → 4. 검증 → 5. 완료 보고

## 1. 파악

**가정하지 않는다. 검색으로 좁히고, 남는 혼란만 질문한다.**

- 같은 기능의 참조와 영향 범위를 먼저 검색한다.
- 여러 해석이 가능하면 선택지와 트레이드오프를 제시한다.
- 테스트·린트·타입 검사·빌드 명령과 기존 검증 관례를 확인한다.

## 2. 완료 조건

**시작 전에 완료 조건과 검증 방법을 작성한다.**

- 완료 조건은 관찰 가능한 동작이나 코드를 읽어 판정할 수 있는 사실로 쓴다.
- 각 조건에 테스트, 검사 명령, diff, 검색 결과 중 적합한 근거를 정한다.

## 3. 구현

**요청 범위 안에서 필요한 부분만 변경한다.**

- 문제를 해결하는 최소한의 코드만 쓰고, 요청과 무관한 정리나 확장은 분리한다.
- 기존 네이밍·구조·오류 처리 관례를 따른다.
- 현재 요구와 도달 가능한 경로에 필요한 처리만 구현한다.
- 공개 API나 공유 계약을 바꾸면 영향받는 호출부를 같은 변경에서 맞춘다.
- 동작을 바꾸면 기존 테스트 체계 안에서 최소 회귀 테스트를 함께 바꾼다.
- 주석은 코드로 드러나지 않는 제약만 적는다.
- 내 변경으로 쓸모없어진 코드만 제거한다.

## 4. 검증

**코드 검토와 실행 검증을 함께 수행하고, 가장 좁은 검증부터 영향 범위만큼 확대한다.**

1. 완료 조건마다 diff, 검색 결과, 테스트 결과 중 충족 근거를 확인한다.
2. 바꾸거나 지운 심볼과 문자열·설정·외부 계약의 참조를 추적하고, 대표·경계·실패 입력 각 1개씩 변경 로직을 줄 단위로 따라간다.
3. 변경과 직접 대응하는 가장 작은 테스트부터 실행하고, 영향 범위에 맞는 린트·타입 검사·빌드로 확대한다.
4. 실패가 변경 때문인지 기존 상태나 환경 제약 때문인지 구분한다.
5. 검증을 통과시키려고 테스트를 삭제하거나 건너뛰거나 완화하지 않는다. 실행 시간이 5분을 넘으면 생략하고 완료 보고에 남긴다.
6. diff를 다시 읽어 불필요한 변경과 디버그 코드·의도하지 않은 `TODO/FIXME`를 제거한다.

## 5. 완료 보고

**휴먼이 결과를 재현하고 남은 검증을 이어받을 수 있게 보고한다.**

- 변경 요약과 완료 조건별 근거를 보여준다.
- 실행한 명령과 성공·실패 결과를 보여준다.
- 실행하지 못한 검증은 이유, 대체 확인, 실행 명령, 기대 결과와 잔여 위험을 남긴다.
